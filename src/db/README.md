# src/db — schema and migrations

Drizzle schema, migrations, and the database client. Nothing else. No business logic — that lives
in `src/core`, which calls into here.

```
schema/       Table definitions, one file per domain area, re-exported from index.ts
migrations/   Generated by drizzle-kit. Forward-only. Never edit an applied migration.
```

## Connections

- The app uses the **pooled** connection string (`DATABASE_URL`). Serverless functions open many
  short-lived connections; the unpooled string will exhaust Postgres.
- Migrations use the **direct** string (`DATABASE_URL_UNPOOLED`) — PgBouncer in transaction mode
  cannot handle DDL reliably. Already wired in `drizzle.config.ts`.

## Rules

- **Constraints belong here, not in application code.** `UNIQUE`, `CHECK`, foreign keys. This
  product cannot tolerate impossible states — a response without a question, a score above the
  maximum, two open bookings for the same exam.
- **All timestamps are `timestamptz`, stored UTC.** Display conversion happens at the edge.
  Booking times are the product; a timezone bug means someone misses their exam.
- Public identifiers — credential IDs above all — must be **unguessable**. Never sequential.
- Soft-delete anything referenced by historical attempts. Questions and exam versions must remain
  readable forever.

## Expected tables

Detailed spec still pending the code-execution decision. Rough shape:

```
users                external_id (opaque, UNIQUE), email, display_name,
                     contact_number NULL, role, created_at, updated_at
certifications       name, slug, level, description, icon_url, marketing_url,
                     external_ref NULL, status
exam_versions        certification_id, status, duration_minutes, pass_mark, published_at
sections             exam_version_id, title, weight, position
questions            type, stem, payload (jsonb), answer_key (jsonb), tags, status
exam_version_questions  join: version, question, section, position, weight
bookings             candidate_id, exam_version_id, scheduled_at timestamptz,
                     booked_timezone, status
attempts             booking_id, exam_version_id, started_at, expires_at,
                     submitted_at, graded_at, result_released_at
attempt_questions    frozen served set + order, per attempt
attempt_responses    attempt_id, question_id, response (jsonb), score
                                                  UNIQUE(attempt_id, question_id)
credentials          attempt_id, public_id (unguessable), holder_name (snapshot),
                     issued_at, expires_at, revoked_at
attempt_events       append-only audit log
```

## Notes on specific columns

**No `exam_slots` table.** Booking is self-scheduled: the candidate picks their own time, so a
booking carries `scheduled_at` directly. There is no capacity, no registration deadline, and no
seat contention.

**`bookings.booked_timezone`** stores the IANA zone the candidate booked in, alongside the UTC
instant. Keep both — it is what reminders display and what you reason about if someone disputes
the time.

**One open booking per exam per candidate** — a partial unique index over active statuses, not a
check in application code.

**`users.external_id`** is the OIDC `sub` from TestMu AI's identity provider. It is the key, not
email; email is a mutable contact attribute refreshed on every login.

**`credentials.holder_name`** is a snapshot taken at issuance. It must not follow later changes to
`users.display_name`, or a name change silently rewrites every credential the person holds —
including the public verification page an employer may already have checked.

**`questions.answer_key`** must never be selected in a candidate-facing query. See
[`docs/conventions.md`](../../docs/conventions.md#answer-key-safety).
